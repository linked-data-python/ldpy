# 2026-09-11 — session 3 : lignes namedtuple dans `for @bindings`

## Ce qui a été fait

Issue GitHub #1 (Erdem Onal) : `for @bindings in rows` refuse les lignes
produites par `pandas.DataFrame.itertuples(index=False)`, qui sont des
`namedtuple`, pas des mappings — `as_bindings_iter` (`ldpy/runtime.py`)
n'acceptait qu'un objet à `.items()`. Consigne de Maxime en commentaire :
investiguer, et dire si d'autres structures ont leur place ici.

Fait, dans `as_bindings_iter` : une troisième branche, après `Bindings` et
les mappings, pour tout objet exposant `_fields` — un appariement positionnel
via `zip(item._fields, item)`, passé à `Bindings.update` (qui accepte déjà un
itérable de paires, pas seulement quelque chose à `.items()`).

`_fields` plutôt que `_asdict()` : c'est l'attribut que `Row`/`_RowSeq`
(le type que rend `m{ … }` d'arité ≥ 2, fiche 016/017) portent déjà pour le
même usage — donc `for @bindings in list(m{ … })` marche du même coup, sans
code séparé, et c'est un deuxième cas d'usage réel couvert par la même ligne.
`_asdict()` aurait exclu `Row`/`_RowSeq`, qui ne l'ont pas.

Fiche 017 mise à jour en place (§ « un mapping quelconque… ») : la nouvelle
branche, pourquoi `_fields` et pas `_asdict`, et ce qui reste dehors —
`dataclasses.dataclass` (ni `.items()` ni `_fields` ; couvrir demanderait
`vars(item)`, une deuxième voie de duck-typing) et le sort de
`ucollections.namedtuple` sur MicroPython, **pas vérifié** : sa mémoire
réduite n'a pas `_asdict`/`_replace`, mais si `_fields` n'est pas exposé sur
les instances côté firmware, `--target micropython` engendrerait le même
`runtime.py` sans que le chemin marche sur l'appareil. Point à trancher
avant de le donner pour acquis, faute d'avoir pu le lancer sur cible depuis
cette session.

Deux tests dans `tests/test_bindings.py` : `for @bindings` sur des
`namedtuple` (l'exemple exact de l'issue), et sur une liste de `Row`
collectée hors de la boucle d'un `m{ … }` — la non-régression sur `[1]`
existait déjà (`test_for_bindings_non_mapping_raises`).
